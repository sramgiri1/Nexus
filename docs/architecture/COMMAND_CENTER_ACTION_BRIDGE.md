# Command Center Action Bridge

**Version:** 1.0
**Date:** 2026-05-08

---

## Purpose

Introduce a safe local action request bridge so the Command Center can
express governed action intent without direct command execution.

---

## Why this follows P32

P32 made the private validation state visible. The next gap was a
mechanism to record *intent* for future governed tasks without wiring
live execution yet.

P33-LOCAL adds the action bridge layer: action requests are validated
through mode, schema, capability, and governance checks, then persisted
to `local-state/runtime/actions.jsonl`. No command is executed; no API
or DB is added.

---

## What the action bridge does

- Accepts a typed action request (`actionType`, `requestedBy`, `source`,
  `mode`, `target`)
- Validates mode boundary (local-private required for private actions)
- Validates action schema and capability
- Detects approval requirements without bypassing them
- Persists the governed action record under the local write boundary
- Emits evidence, audit, and runtime event records through the existing
  governed path
- Returns a routing result with status (`validated`, `blocked`)

---

## No direct execution

The action bridge does **not**:

- execute `npm test` or any shell command
- call providers (Anthropic, OpenAI, or OpenRouter)
- open network connections
- access the database or any API server
- mutate private project source files
- allow browser filesystem writes
- expose an API endpoint

The `requestedCommand` field on every action is always `null`. The
`mutationRequested` flag is always `false`. These are validated at the
schema level and enforced by the store before the record is written.

---

## No UI mutation

The Command Center panel shows:

- Action bridge readiness (from generated static snapshot)
- Last demo action status
- Recent action requests (read-only)
- CLI command: `npm run action:bridge-demo`
- Note: "UI cannot execute directly"

There are no mutation buttons or `onClick` handlers that submit commands.

---

## No API, No DB

Because no API server exists yet and no DB is wired, the browser UI reads from a browser-safe
static snapshot generated by `scripts/action-bridge-demo.js`. The snapshot
is written to `dashboard/src/data/actionBridgeSnapshot.js` and committed
as a static data module.

---

## Governed flow

```text
action request
  → mode boundary check
  → action schema validation
  → capability check
  → approval detection (not bypass)
  → local write boundary
  → actions.jsonl append
  → evidence + audit + event append
  → routing result
```

---

## Action store file

Actions are appended to `local-state/runtime/actions.jsonl` using the
same `assertWritePathAllowed` guard that protects all runtime writes.
Each record is redacted, sanitized, and checked for secret-like content
before writing.

---

## Supported action types

| Action type | Mode required | Approval required |
|---|---|---|
| `private_project_backend_validation_request` | local-private | Yes |
| `refresh_private_validation_snapshot` | local-private | No |
| `demo_noop` | demo | No |

---

## CLI command

```bash
NEXUS_MODE=local-private npm run action:bridge-demo
```

Creates one governed action request and routes it through local
governance. Does not execute `npm test` or any other command.

---

## What is not implemented in P33

- Live API endpoint
- DB persistence
- Real execution dispatch
- Provider calls
- Approval workflow wiring for action bridge
- UI form submission
- Batch action queuing
